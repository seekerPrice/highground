## Primary evidence

- [data.gov.my flood endpoint](https://api.data.gov.my/flood-warning): HTTP 200, an unwrapped JSON list of 1,276 station rows. Exact response bytes are in `api/fixtures/flood_warning_sample.json`; request URL, HTTP status and capture clock are in `api/fixtures/provenance.json`. 725 water-level timestamps are null; latest non-null timestamp is `2024-02-23 14:45:00`. These are historical readings, regardless of their timezone interpretation. The response includes coordinates, district/state, current level, `water_level_indicator`, device statuses and separate thresholds. The first row's thresholds are not monotonically ordered. Thresholds are not used to manufacture severity.
- [JPS English station legend](https://publicinfobanjir.water.gov.my/main/?lang=en) distinguishes Normal, Alert, Warning, Danger and Error. [JPS Malay legend](https://publicinfobanjir.water.gov.my/) distinguishes Normal, Waspada, Amaran, Bahaya and Ralat. [JPS October 2022 publication](https://www.water.gov.my/jps/modules_resources/bookshelf/jps_UPDATEs_OKT_2022/jps_UPDATEs_OKT_2022.pdf) describes waspada as an increase from normal, amaran as approaching flood level, and bahaya as overflowing. HighGround maps these distinct source indicators to Watch, Warning and Danger respectively; the raw indicator is retained. The initial ALERT→Warning implementation was corrected after Astra review. `water_level_status` ON/OFF is device state, not risk severity.
- [data.gov.my weather endpoint](https://api.data.gov.my/weather/warning): HTTP 200, unwrapped list of four records at capture, with nested `warning_issue`, issued/title, validity window, headings and bilingual prose. Two marine records mention heavy rain; the land thunderstorm record names districts in prose; a no-advisory cyclone record lacks a validity window. Original bytes are in `api/fixtures/weather_warning_sample.json` with provenance.
- [Official weather documentation](https://developer.data.gov.my/realtime-api/weather) identifies MET Malaysia as source, updates warnings when required, and documents the warning's issued/validity/title/prose fields. Structured location fields and district ID prefixes are documented for the **forecast** schema, not warning records. They must not be borrowed as an invented warning schema. [Official request query documentation](https://developer.data.gov.my/request-query) documents filtering, sorting and optional limit; no offset or page cursor is documented. These clients request the complete endpoints without a limit and reject unexpected wrapped shapes.

## Decisions and contract

- User approved the configurable 90-minute maximum age for station readings via root/Astra. This is an engineering exclusion threshold, not an asserted provider cadence. Exact boundary is eligible; older readings are excluded. Missing, invalid, future, error/device-OFF and non-finite/out-of-range records are excluded. Source health carries rejection counts separately from eligible warnings; an empty response is not labelled confirmed clear.
- Neither inspected API response nor official warning documentation establishes timezone semantics for their offset-free timestamps. Default parsing rejects these as `unverified_timezone`. Callers may supply a `tzinfo` only after verifying that source's semantics; tests using Asia/Kuala_Lumpur are synthetic boundary tests, not proof of the API timezone. No live current warning acceptance is claimed.
- Common `Warning` records carry source, source identity, level, aware observation time, optional validity end, attributed geography, reason and raw indicator. `SourceResult` separately reports current/degraded/stale/unsupported/empty/unavailable status, counts, diagnostics and current NORMAL recoveries. Source availability must be displayed independently of alert count.
- Weather supports the captured land type `Thunderstorms Warning` only when the text includes heavy rain, contains no marine scope markers, has a current verified validity window and receives caller-supplied reviewed district/state attribution for that **exact record fingerprint**. Fingerprints identify exact content; they do not authenticate it. No mappings ship by default. Changed prose invalidates an old mapping. Marine and unrecognized types remain excluded even with a mapping. New weather types require a reviewed primary-source mapping; prose keyword-only district extraction is deliberately absent. Default live weather acceptance awaits both timezone verification and geographic attribution.
- `fetch_warnings` accepts an owned `httpx.AsyncClient` (transport/timeout injectable), an aware clock, age configuration and verified timezone/geography configuration. HTTP/network/invalid-JSON/invalid-top-level failures remain explicit and independent per source. No external cloud/application endpoint is introduced.
- `dedupe_warnings` is a pure transition taking prior episode state and returning emitted warnings plus next state. Keys are source + station/warning ID. It emits first observations and escalation, suppresses repeated/lower levels, rejects time reversal, and permits later episodes after an observation-time gap or a newer **eligible current NORMAL** recovery. Recovery timestamps persist as tombstones to reject old warnings even on later out-of-order polls. An unavailable/stale/empty poll must never clear state. Recoveries use source-prefixed IDs (`jps:<station_id>`) consistently in `SourceResult.resolved` and dedupe state. Task 7 must commit dedupe state and event creation atomically in persistent storage; the adapter itself does not promise cross-process exactly-once delivery. Stable event IDs include source identity, episode start and level.
