# Task22 pure contract candidate

This preparation adds only `api/outcome_models.py`, `api/outcomes.py`, `api/calibration.py`, their two focused pure test files and this note. Shared application, analytics schema, configuration, catalogs, frontend and runtimes remain unchanged. It is not Task22 acceptance.

## Frozen interfaces and facts

`OutcomeEpisode` binds the confirmed shop/episode and shop geohash6, explicit first-event time/closure, owner snapshot, real/demo generation and bounded delivery history with complete/incomplete/overflowed status. The integration adapter must use the stored target's actual episode identity, not event/request IDs or current risk after recovery. ActiveRisk has no authoritative `started_at` field; an explicit confirmed episode ledger must preserve the first event time rather than inventing current time. Accepted delivery maps only actual Telegram accepted status/sent_at to `accepted_at`; virtual completion stays separate. Known synthetic fixtures have explicit provenance and never count as Telegram acceptance.

`first_owner_response` requires trusted current-owner identity/role/shop and observation ordering inside that confirmed episode. Its first response is immutable. Answers are no/street_only/entrance/inside; depth is optional whole centimetres0..1000, never inferred. The separate owner_report entrypoint permits an inside report without claiming that an alert was missed. Sender ownership and observation timestamps must be derived/validated against actual stored facts, not accepted as client assertions. `prompt_due` uses earliest Telegram acceptance plus configurable positive default6hours or explicit closure; no owner, active Danger or obsolete demo generation defers it. No scheduler or automatic clock was installed.

`OutcomePrompt` carries explicit realm/generation. Public synthetic `outcome_coverage` counts distinct shop/episodes, first responses, missing/unknown and accepted, virtual, fixture or ambiguous prompts separately. It rejects cross-generation prompt attribution and out-of-episode responses. Neither response count nor water reports are called accuracy or independent verification.

`decide_calibration` takes a scoped versioned `CalibrationState`, bounded `CalibrationEvidence`, current aware time and already-consumed canonical keys. New first responses must match stored episode, area, realm/generation and the30-day observation/response window. Shrinking requires at least five responses eligible for actual accepted Warning/Danger coverage; street_only/entrance/inside count as water and no as no water. Missing responses are excluded from that ratio, not converted to no. The threshold is strictly below0.3 and step is10%, clamped0.5–1.5. Explicit labelled synthetic-fixture history may demonstrate the rule in demo state without becoming accepted Telegram history or real calibration.

Growth requires a first owner_report inside response and complete history proving no earlier accepted alert. Earlier sending/uncertain/unresolved or virtual history suppresses growth. Proven later acceptance does not retroactively erase an earlier eligible inside observation. The adapter must establish that ordering from trusted stored facts. Canonical shop/episode/realm hashes are consumed alongside response IDs, so a changed opaque ID cannot replay the same outcome scope. A no-change evaluated batch is consumed/versioned too. Conservative implementation interpretation confirmed by Astra: one atomic step per evaluated batch; proven growth wins simultaneous shrink evidence, and both evaluated scopes are consumed to prevent immediate undo/replay. This is not a new explicit user approval.

`freeze_radius` records base and effective radius, geohash area, realm/generation, source/level/purpose, applied multiplier and evidence version. It applies only to demo/shop_report Warning dispatch. Official JPS/MET including simulations, every Danger, fixed500m corroboration and `/check`2km are unchanged. Effective radius can exceed the original request bound (10,000m ×1.5 =15,000m); preserve it separately. Existing plans require an exact immutable-scope match and retain their first calibration on retry; a Warning plan cannot be reused for Danger/official/fixed-query scope. The dispatch adapter binds this plan to the event/shop target before storing it, never changes EventRequest.radius_m or recomputes an existing target.

## Evidence

Geohash6 longitude-first bisection matches the primary [PostGIS ST_GeoHash vector](https://postgis.net/docs/manual-dev/en/ST_GeoHash.html) and [author's encoding reference](https://www.movable-type.co.uk/scripts/js/latlon-geohash/docs/Geohash.html). Tests use latitude48/longitude−126 → c0w3hf and52.205/0.119 → u120fx, with equator, antimeridian, poles and invalid coordinate boundaries. No dependency was added.

Observed behavioral RED→GREEN: a later answer replaced the first response; four responses improperly shrank; an old-generation prompt counted in current coverage; an existing calibrated Warning plan was reused for Danger, and a persisted plan could decode inconsistent or authoritative calibration. Those defects now have passing regressions. Controlled threshold `<`→`<=` and official-source eligibility mutations failed the exact0.3 and authoritative-radius tests. Some new interfaces first failed as unimplemented, not as deployed defects; that distinction is retained.

Final focused command: `.venv/bin/python -m pytest api/tests/test_outcomes.py api/tests/test_calibration.py -q`. Thirteen tests passed, zero skips. They cover current owner/worker/shop/episode, immutability, due/closure/Danger/reset, missing coverage, repeated recipients, stale prompt realm, disjoint first scopes,30-day edges, five responses, threshold, growth ordering/uncertainty, clamps, synthetic separation, precedence, no replay and frozen targeting scope. No SDK, model, emulator, production build or runtime call occurred.
